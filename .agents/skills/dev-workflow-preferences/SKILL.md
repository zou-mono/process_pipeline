# 个人通用开发偏好与工程规范 (Developer Workflow & Preferences)

本技能沉淀了用户在结对编程过程中的通用开发习惯、Git 提交规范、UI/交互审美偏好以及工程验证准则。在任何项目的日常开发、方案讨论、代码实现与版本提交中，请始终遵循以下规范，并随后续对话持续演进更新。

---

## 1. Git Commit 规范与提交时机准则

### 1.1 提交时机铁律（未经明确指令绝不自动 Commit）
- **先验证汇报，后听令提交**：完成代码修改、编译与自动化测试后，**严禁擅自执行 `git commit`**。必须先将修改内容与验证结果反馈给用户，由用户审阅或实机确认。
- **触发条件**：仅当用户明确发出提交指令时，才执行提交操作。常见触发语包括：
  - *“现在的修改先 commit 一次”*
  - *“这个可以 commit 一次”*
  - *“这个改好直接提交一次”*
  - *“可以，先提交一次”*

### 1.2 Commit Message 格式规范
始终采用 **`<type>(<scope>): <中文简明描述>`** 的单行结构化格式：

```text
<type>(<scope>): <动词开头的中文核心改动与效果描述>
```

#### 常用 `<type>` 分类速查
| Type | 适用场景 | 典型示例 |
| :--- | :--- | :--- |
| `feat` | 新增功能、新增交互能力或业务规则 | `feat(ui): 分离列表问题描述与解决方案并统一软件帮助式悬停提示规范` |
| `fix` | 修复 Bug、状态失效、焦点异常或边界缺陷 | `fix(ui): 修复标记状态后Undo/Redo失效并实现右键菜单状态项上下文感知显隐` |
| `style` | 界面视觉微调、按钮文案/图标精简、主题样式对齐（不改业务逻辑） | `style(ui): 将通用消息弹窗底部确认按钮改为纯文字'确定'按钮` |
| `refactor` | 重构代码结构、提取公共组件/服务、解耦模块（不改变外部行为） | `refactor(core): 提取通用状态流转校验逻辑并精简事件处理` |
| `perf` | 性能优化（算法加速、批处理优化、渲染减负、虚拟化） | `perf(data): 优化大数据量列表筛选与视图刷新性能` |
| `test` | 新增或完善单元测试、集成测试断言 | `test(core): 补充状态切换Undo/Redo与菜单显隐回归测试` |
| `chore` | 构建脚本、工程配置、依赖项或开发技能包（Skill）维护 | `chore(skill): 更新个人通用开发偏好与Git提交规范技能包` |
| `docs` | 仅更新设计文档、注释或说明材料 | `docs(readme): 更新模块架构说明与测试运行指南` |

#### 常用 `<scope>` 划分原则
按改动所属的**功能职责或架构层级**简短命名，例如：
- `ui`：界面视图、弹窗、表格/树控件、工具栏、状态栏、悬停提示及交互逻辑
- `core`：核心基础架构（命令系统、Undo/Redo、状态机、事件总线、公共基类）
- `data` / `model`：数据结构、持久化、序列化、状态存储
- `service` / `api`：业务服务层、外部接口调用与通信
- `theme`：主题配色、样式模板、图标资源
- `test`：单元测试与自动化回归测试
- `config` / `skill`：工程配置、开发工作流与 AI 技能定义

#### 描述写作要点
1. **单行精炼、直奔主题**：用 `动词 + 核心对象 + 关键效果` 一句话讲清楚改动本质，句尾不加句号，不写冗长的多段式空洞套话。
2. **体现“做了什么”与“解决了什么”**：如 `修复...并实现...`、`分离...并统一...`、`将...改为...`。

### 1.3 暂存区完整性检查
- 在跨平台或 Windows 仓库中，注意文件系统大小写与 Git 索引（Index）路径的一致性。
- 提交前先执行 `git status -s` 核对所有改动文件，确保关联的代码、资源与测试文件完整暂存，无遗漏或误提交。

## 2. 结对编程与方案对齐工作流

### 2.1 “先对齐思路，再动手写代码”
- 当用户探讨设计改进、询问优雅解法，或明确表示 *“你想一下有什么优雅的解决方案，先不改，给我看一下你的思路”* 时，**严禁直接修改任何代码文件**。
- 先给出 **2～3 个层次清晰的备选方案**（如方案 A / 方案 B / 方案 C），明确标出 **`[推荐]`** 方案，阐述各方案的视觉/交互效果与优劣。
- 待用户拍板（如 *“可以，按你的思路改吧”*）或补充微调意见后，再开始编写代码。

### 2.2 方案设计必须主动考虑的交互与业务边界
在设计 UI 与交互方案时，应主动思考并向用户交代以下边界情况：
1. **单选 vs 多选（Multi-Selection）**：
   - 选中单条记录时，展示该记录的完整详情与针对性解决方案；
   - 按住 `Ctrl` / `Shift` 选中多条记录时，展示**聚合统计摘要与批量操作引导**（如：`已选中 N 项（状态A X，状态B Y...）— 可右键批量标记状态或执行批量处理`）。
2. **窄列截断与原有功能兼容**：
   - 新增自定义悬停提示（`ToolTip`）或交互时，绝不能破坏原有的“列宽不够时悬停查看完整单元格文本（如长文本、完整坐标、完整路径）”功能。
   - 应将单元格自身完整文本自然融合进悬停卡片中（例如当悬停在非描述列时，在卡片头部下方自动附带 `当前列 (列名)：<完整单元格内容>`）。
3. **工具可用性兜底**：
   - 有自动化修复/辅助工具的，说明交互操作；没有自动工具可调用的，明确提示需要人工核查和编辑。

## 3. 通用 UI / 交互与软件文案设计准则

### 3.1 克制、清爽、去冗余的界面风格
1. **拒绝冗余预览栏与视觉堆砌**：
   - 优先复用现有的底部状态栏（`StatusBar`）与悬停提示卡（`ToolTip`）承载扩展信息，不要轻易增加常驻的“底部详情预览面板”挤压核心数据表格的可视空间。
2. **对话框确认按钮保持纯文字**：
   - 通用消息框、报错/确认弹窗底部的操作按钮（如 `确定`、`取消`）直接使用干净利落的**纯文字按钮**，不需要画蛇添足地添加打勾/叉号图标（顶部主工具栏的图标按钮除外）。
3. **未执行/空白上下文的克制占位与状态栏联动引导**：
   - 当打开新文档或切换至尚未执行过任何命令的空白上下文时，导航树/分类区**绝不凭空预设某个具体的业务规则节点**（避免给用户造成“已执行过该项任务”的误导），同时**也不完全留白**，而是显示一行无子节点的轻量提示项（如 `暂未执行核查`），并在底部状态栏同步给出明确的操作引导（如 `当前文档尚未执行核查，请点击工具栏【一键全量核查】或【单项核查】`）。

### 3.2 “问题描述”与“解决方案”严格分离规范
在数据列表/表格（`DataGrid` / `Table`）及相关详情展示中，严格执行职责分离：

1. **表格单元格（问题描述/备注列）只写客观事实**：
   - 单元格文本只负责陈述**“发生了什么问题或当前客观状态”**。
   - **严禁**在每一行的单元格文本里重复拼接 `“点击可查看…右键可一键…”` 等操作说明，避免单元格内容过长，保持表格紧凑、干净、易扫读。

2. **悬停提示卡（Hover ToolTip）与状态栏采用“软件帮助式”统一规范**：
   - **悬停卡片固定结构**：
     - **卡片头部**：`[编号/标识] 类别 · 当前状态`（若鼠标悬停在坐标、名称等非描述列上，次行显示 `当前列 (列名)：<完整单元格值>`）
     - **正文第一段**：`【问题描述】<客观异常事实描述>`
     - **正文第二段**：`【解决方案】<描述性软件帮助语句>`
   - **【解决方案】文案编写准则**：
     - 定位类似**软件内置帮助文档**，用自然、通顺的描述性语句把解决方案的**功能、要点、操作方式**写清楚即可（例如：`【解决方案】点击行可查看关联详情，右键可一键执行绑定修复`）。
     - **不要过度机械地罗列菜单层级或具体按钮全称**。
     - **无自动修复工具时的兜底规范**：如果该类问题没有自动化工具可直接调用，必须明确交代 **`需人工核查和编辑`** 并简述核查要点（例如：`【解决方案】需人工核查和编辑（双击定位至目标项，核对参数并手动修正）`）。

### 3.3 右键菜单（ContextMenu）上下文感知与状态同步
1. **状态切换项上下文感知显隐**：
   - 右键菜单中的状态流转或分类切换操作项，必须根据**当前所处的分类视图节点**以及**当前选中项的实际状态**动态控制显隐：
   - **绝不展示当前已处于的状态**：如果当前已经在某个状态节点下（或选中项本身已是该状态），右键菜单中不应再出现切换到该当前状态的按钮，而只展示**可切换过去的其他目标状态**。
2. **Undo / Redo 与命令可执行状态实时同步**：
   - 任何状态变更或数据修改进入 Undo/Redo 栈后，快捷键（`Ctrl+Z` / `Ctrl+Y`）、工具栏撤销/重做按钮以及右键菜单项的可执行状态（`CanExecute`）必须立即同步刷新，确保操作可逆且视图实时更新。

## 4. 编译构建与自动化验证闭环

1. **零错误零警告标准**：
   - 每次修改完成后，必须通过编译构建检查，确保 `0 个错误，0 个警告`。
2. **不打断调试会话的自动化验证**：
   - 优先通过单元测试或无头（Headless）自动化回归测试验证改动的正确性。
   - 当用户正在进行实机联调导致默认输出目录文件被进程锁定时，自动采用备用构建配置或独立测试输出目录完成编译与测试闭环，不要中断流程或要求用户频繁关闭调试环境。

## 5. 技能自演进与动态维护机制 (Continuous Self-Evolution)

本技能文档是一个**持续演进的活文档（Living Skill）**。在后续的所有对话中，Agent 必须执行以下自维护职责：

1. **主动捕捉新偏好**：
   - 当用户在对话中针对代码规范、架构设计、UI 交互细节、提示文案、测试方式、Git 工作流或沟通方式提出新的偏好、纠正既有做法或表达明确倾向时（例如：*“以后这类问题都这样处理”*、*“这个地方不用这么复杂，直接…”*、*“我比较喜欢…的风格”*），应立即识别出这是用户的长期开发偏好。
2. **提炼为通用规则**：
   - 将新捕捉到的偏好剥离特定项目的临时业务名词，提炼为清晰、通用的开发准则（包含正反例或使用场景）。
3. **双端自动同步更新**：
   - 在完成用户当前开发任务的同时，主动更新本技能文件，并保持以下两个位置同步：
     - **全局技能库**：`C:\Users\mono_ws\.gemini\config\skills\dev-workflow-preferences\SKILL.md`
     - **当前工作区技能库**（若工作区存在该文件）：`.agents/skills/dev-workflow-preferences/SKILL.md`
   - 更新后在回复末尾简短告知用户已将新偏好沉淀至 `dev-workflow-preferences` 技能中。
